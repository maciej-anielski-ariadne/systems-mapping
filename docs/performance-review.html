Executive verdict

The app now meets its automated older-hardware interaction gates at 300 boxes

The focused architecture work paid off. Simulation no longer rebuilds the map, selection and Atlas repaint through retained references, scale algorithms are bounded, and imports prepare away from the interface thread.

At the agreed 300-box scale under 6× CPU slowdown, selection measured 33 ms p75, Simulation entry 105 ms, exit 74 ms and slider response 30 ms. Atlas now paints meaningful structure in 160 ms, reaches its complete state in 259 ms and reopens a completed view in 61 ms p75. Startup layout shift remained 0.00021 with no boot transition runs.

The result is not a claim of universal speed. A restored 300-box map still has a 546 ms p75 longest startup task in the final isolated run, complete Atlas enrichment deliberately follows its first structural paint, and very large maps can still be expensive after the user explicitly accepts them.

P1.01Boot animates the entire application from a three-column shell to reading mode
MeasuredCold startHigh confidence

The HTML initially paints the default 240 px / 340 px side panels. Only after the eager module graph executes does applyUiMode() add reading mode, reducing both tracks to zero through a slow grid-template-columns transition. On a constrained CPU, first paint sometimes lands before that transition and the map visibly stretches across the viewport.

EvidenceDefault grid at assets/css/03-app-shell.css:22–43; transition and reading tracks at :360–370; mode is first applied after every module import at assets/js/18-main.ts:19–59 and :95–97. At 6× CPU, 3 of 12 cold loads recorded CLS around 0.177, sourced to MAIN.viz-container and sidebar content; the other nine were 0.003.

Implemented: the document starts in app-booting, restored mode and panel state are applied without duplicate panel renders, and transitions are enabled only after two animation frames. Four 6×-CPU reloads recorded zero boot transition runs and CLS 0.00021.

P1.02Simulation entry synchronously rebuilds the sidebar, every map element, and the detail panel
593 ms300 boxesHigh confidence

toggleSimulationMode() performs a synchronous full-surface transaction. The central renderer serializes and replaces the complete SVG. At 300 boxes the map sits just below the 400-node / 2,000-edge virtualization boundary, so all 300 nodes and 299 links are rebuilt.

Evidenceassets/js/14-simulation-panel.ts:508–545; full render and innerHTML commit at assets/js/11-rendering.ts:1155–1580, especially :1565–1568; thresholds at :413–415. Median 6×-CPU entry: 593 ms. The 400-box profile still took 707 ms despite culling to 264 nodes and 263 links.

Implemented: map elements and their resting fills survive Simulation entry and exit; Simulation values are inserted lazily, then updated in place. In the final isolated 6× run, entry fell from the 593 ms baseline to 105 ms p75 and exit measured 74 ms p75.

P1.03Atlas open spends far more time replacing and painting SVG than building the model
345 msDOM dominatedHigh confidence

The Atlas engine is not the ordinary 300-box bottleneck. Opening Atlas constructs a graph and Atlas, then generates the full picture string, replaces the stage DOM, paints all flows and circles, frames the view and starts reveal behavior.

Evidenceassets/js/21-atlas-view.ts:401–434 and :714–725. In a partitioned 6× run, buildGraph took 1.4 ms, buildAtlas 20.2 ms and measurement 0.2 ms, while the synchronous open path took 196 ms and open-to-paint 345 ms. A repeated full Atlas render took 79–85 ms at 300 boxes.

Implemented after owner decision: Atlas commits real paths, circles and gates first, then yields across a paint boundary before adding labels, feedback-wheel controls, current Simulation state and the inspector. The stage exposes deterministic structure / complete phases, remains inert while busy and cancels stale work on close or start changes. Meaningful structure painted in 160 ms, completion reached 259 ms and a completed same-start Atlas reopened in 61 ms p75.

P1.04Selection patches styling, but still scans the whole rendered slice and rebuilds the detail panel
208 ms maximumCore workflowHigh confidence

A normal selection is fast, but the first selected box can cross the 200 ms line. Trace state scans all visible nodes, selection styling queries and walks every rendered node and edge, and the detail panel opens through the same grid transition.

Evidenceassets/js/09-graph-selection.ts:180–233 and :281–311; DOM scan at assets/js/11-rendering.ts:1606–1686; selection notification at :1712–1719. The 300-box 6× profile had a 19 ms selection median but a 208 ms median-of-run maxima; a separate end-to-second-paint probe measured about 305 ms.

Implemented: rendered nodes and links are indexed by identifier, selection styling compares the previous and next sets, and only changed elements are repainted. The final isolated 6× run measured 33 ms p75 and 37 ms maximum.

P1.05CSV import reads and multiplies arbitrarily large files in main-thread memory
Memory safetyUnbounded inputHigh confidence

The picker validates only the filename extension, reads the entire file into one string, builds a second array of record strings, then cell arrays and row objects while the earlier representations remain live. On low-memory hardware this can cause garbage-collection storms or tab termination before the local-storage quota warning is relevant.

Evidenceassets/js/16-file-io.ts:38–57; record retention at assets/js/05-csv-parser.ts:87–131; row construction at :133–178; parsed sections remain live during runtime-array construction at assets/js/06-data-loader.ts:619–622 and :1073–1083. Parser-only probe: 1.49 MiB/10k rows → +32.6 MiB immediate heap; 7.98 MiB/50k → +282.7 MiB; 16.09 MiB/100k → +552.0 MiB.

Implemented after owner decision: there is deliberately no hard envelope. File bytes transfer to a dedicated Worker, records are parsed in one pass, pure transaction-gating checks and counts run off-thread, and progress can be cancelled without touching the current map. At 5 MiB, 1,000 boxes or 2,000 links, exact counts and a performance warning precede explicit Open map / Cancel choices.

P1.06Review attribution and validation become quadratic and run synchronously during load and edits
ScaleMulti-secondHigh confidence

Drift attribution independently walks upstream for every drifting box; snapshot validation filters the entire edge list once per node. Load currently attributes findings twice around Review reconstruction, and topology/calculation edits repeat the work.

Evidenceassets/js/22-review.ts:102–140; duplicate load invocation at assets/js/06-data-loader.ts:1196–1208; per-node edge filter at assets/js/22a-review-model.ts:235–265; mutation refresh at assets/js/16f-canvas-mutations.ts:103–110. On an Apple M5, drift attribution grew from 31 ms/500 nodes to 836 ms/4,000 and 3.73 s/8,000. Stable validation reached 403 ms at 8,000 nodes/20,000 edges before older-hardware slowdown.

Implemented: attribution builds the drifting subgraph once, Review snapshots cache incoming links, and the overwritten first attribution pass is removed. The 8,000-node attribution probe fell from 3.73 s to about 29 ms; a 16,000-node / 40,000-link Review validation completed in about 51 ms on the test machine.

The real-browser 300-box test is valuable, but its 500–5,000 ms limits allow interactions that already feel frozen. It samples five selections, runs without CPU throttling, does not count long tasks or CLS, and omits Review, dense collapse, Atlas menu scaling, tutorial idle cost and the 399/400 virtualization boundary.

Evidencetests/browser/app.acceptance.spec.ts:623–857. The current test passed with all actions inside budget while the separate 6× trace recorded a 593 ms Simulation entry, 11–12 long tasks per run and a median 200 ms longest task.

P2.02Virtualization bounds live DOM, not full-edge scans or model work
Dense mapsMeasured boundaryHigh confidence

At 400 nodes the renderer correctly culls map DOM, but every slice still loops over every render edge and performs recursive Bézier intersection tests. Review, Atlas and simulation model work remains whole-map. This explains why 400-box interaction can be slower even with fewer live elements than the 300-box case.

EvidenceThresholds and culling at assets/js/11-rendering.ts:399–430; full-edge cull loop at :1338–1349; second hit-path test at :1382–1388. At 400 boxes, only 264 nodes/263 links were rendered, yet 6× Simulation entry was 707 ms and Atlas open 603 ms.

Implemented: cached Bézier geometry is subdivided into exact tile candidates, with a bounded always-candidate path for exceptionally long curves. An edge-heavy regression fixture confirmed 486 candidates from 2,498 links—about 80.5% pruned before exact intersection checks.

P2.03Atlas lane discovery becomes quadratic in large sibling families
Atlas scaleEngineHigh confidence

Candidate lane families pair-compare members for adjacency and then pair-compare surviving neighbourhoods. One broad family can dominate before any SVG is created.

Evidenceassets/js/20-atlas-engine.ts:217–277 and :327–361. Star-family probe on an Apple M5: 251 nodes 11 ms; 1,001 nodes 72 ms; 2,001 nodes 276 ms; 4,001 nodes 1.15 s.

Implemented: Atlas builds neighbour sets once, groups identical signatures, and performs exact weighted Jaccard comparisons only where still needed. The 4,001-node star-family probe fell from 1.15 s to about 31 ms.

P2.04Collapsed-link routing restarts hidden-subgraph traversal for every boundary edge
Dense topology188–201 msHigh confidence

When a row, column or category hides a dense region, each visible-to-hidden boundary edge receives fresh traversal state. Multiple entries from the same source repeat the same hidden work.

Evidenceassets/js/10a-collapsed-edges.ts:148–182, synchronously invoked by assets/js/10-filters.ts:118–138. A 40-source/30-hidden/2,220-edge fixture took 188–201 ms at 6× CPU; existing coverage uses one visible source and nine hidden nodes.

Implemented: collapsed-edge routing now performs one multi-entry hidden-frontier traversal for each visible source. The dense regression fixture completes in about 7 ms on the test machine.

P2.05Restored startup repeats whole-map derivation and rendering in one long task
383 ms long taskSaved mapsSource confirmed

Loading stored CSV performs indexes, validation, layout, simulation, Review and full-surface renders. The separate restored-UI phase then recomputes values and renders again, potentially toggling Simulation and selecting a box before the browser can paint.

EvidenceBoot order at assets/js/18-main.ts:99–140; load work at assets/js/06-data-loader.ts:1190–1229; restored recompute/render at assets/js/04a-storage.ts:277–302. Saved 300-box startup at 6× CPU: 440 ms load, 468 ms LCP and one 383 ms median long task.

Implemented: startup no longer applies reading mode before applying the saved mode, and restored UI avoids a second panel render during hydration. A structural 300-box load still produced a 546 ms p75 longest task in the final isolated run, but first contentful paint was 660 ms p75 and the shell no longer visibly transitions through the wrong layout.

P2.06Closing Bulk edit keeps its deep-cloned graph resident
Concrete retentionLow frequencyHigh confidence

Opening Builder deep-clones nodes and edges into state.builder. Closing removes UI and storage but leaves those arrays live. A 4,000-node/10,000-edge synthetic clone remained after forced collection and retained at least 1.31 MiB with short shared strings.

EvidenceClone at assets/js/16a-builder-state.ts:182–237; close path at :116–126.

Implemented: closing Builder clears its cloned node, edge, parameter and review arrays plus transient sort/validation state. Focused lifecycle coverage verifies the data is released.

P2.07Hosted delivery should not use the offline package as its only build
ConditionalHosted useMeasured counterfactual

The self-contained file is exactly right for email, USB and double-click use. It is not the fastest hosted entry because the browser cannot paint until a large HTML response containing JavaScript, CSS and base64 fonts arrives.

EvidenceInlining is deliberate at vite.config.ts:13–25. A standard Vite counterfactual cut cold transfer from 343 KB to about 258 KB. At 400 Kbps + 6× CPU, FCP improved from 6.99 s to 1.57 s and load from 7.16 s to 5.58 s.

Implemented in the repository: npm run build still produces the self-contained offline file; npm run build:hosted now emits hashed CSS, JavaScript, fonts and a separate CSV Worker. CI builds both. The deployment platform must still assign immutable caching to hashed assets and revalidation to index.html.

P3.01Tutorial target tracking performs layout reads and connector writes every animation frame
HypothesisContinuous costMeasure before changing

While a target exists, a perpetual frame loop queries candidate targets, checks computed style, measures the target and card, and rewrites the connector even when neither moved. The mechanism is confirmed; user impact was not isolated in this audit.

Evidenceassets/js/26-tutorial.ts:390–475 and global invalidation listeners at :1744–1750.

Implemented: connector geometry is marked dirty by step changes, resize, scroll, drag and relevant DOM mutations, then coalesced into one frame. With no change, no animation-frame loop runs.

Performance remains a tested contract

Protect these strengths

The review found more focused engineering than waste

Single-request offline delivery

No dependency chain, no service worker requirement, minified code, no source maps, local fonts and a compact Brotli form. Local/offline cold startup is already strong.

Incremental simulation engine

Slider work is coalesced to one solve and repaint per frame, and downstream solving is incremental. Warm 300-box solver updates were 1–6 ms at 6× CPU.

Pan, zoom and drag scheduling

Native scrolling, passive listeners, idle-time slice redraw, compositor zoom gestures, spatial hit indexes and overlay-only drag painting avoid obvious high-frequency rebuilds.

Builder virtualization

Rows are windowed, selects are upgraded lazily, and validation/sort results are memoized per render pass. Scale-focused suites remain green.

Search stays cheap

Search caches normalized data, caps rendering at eight results and debounces input. Even a 5,000-node long-text corpus stayed around 10–22 ms at 6× CPU.

No general leak was confirmed

Forced-GC heap at 400 boxes stayed between 5.22 and 5.31 MB across baseline runs. The observed listeners were stable and mostly delegated or lifecycle-guarded; the specific Builder retention defect is now cleared on close.

Three tempting changes remain unwarranted. Do not remove the tutorial for a roughly 32 ms baseline cold-start gain; do not rewrite the SVG architecture now that retained updates meet the gates; and do not impose a hard file-size ceiling when cancellable preparation and explicit consent meet the owner’s requirement.

Method

  • Three parallel specialist passes covered main-thread rendering and interaction, bundle/startup/network, and scale/memory/lifecycle. A second parallel implementation pass owned retained surfaces, Worker/import behavior, and delivery compatibility. The coordinator independently reran the complete checks.
  • The primary workload is the previously agreed 300-box scale. Separate adversarial fixtures establish where unbounded input or algorithmic shape can overwhelm that happy path.
  • Chrome documents 6× CPU slowdown as a useful constrained-device profile. Core Web Vitals “good” reference points are LCP ≤2.5 s, INP ≤200 ms and CLS ≤0.1 at the 75th percentile. See Chrome performance guidance and web.dev’s Web Vitals reference.
  • Action timings in this report are controlled lab observations, not field telemetry. No real-user INP distribution exists, and no actual low-end device was available in this run.
  • The dedicated Chrome DevTools profile was locked by another running inspection session, so it was not terminated. Equivalent CPU throttling, Performance Observer data and Chrome DevTools Protocol metrics were collected through isolated Playwright Chromium instead.
  • Playwright now refuses to reuse an existing preview server and supports explicit offline/hosted port overrides. This prevents a foreign checkout on port 4173 from being mistaken for the artifact under test; the final verification used fresh ports 4185 and 4186.

Scope boundaries

  • This report now covers both the baseline review and the implemented remediation in the isolated codex/performance-older-hardware worktree.
  • The report covers reading, editing, Simulation, Atlas, Review, Bulk edit, tutorial, import, persistence, rendering, network delivery and memory lifecycle.
  • GPU raster cost, energy draw, thermal throttling and accessibility beyond the startup semantic snapshot need actual-device or dedicated tooling follow-up.
  • Production hosting cache headers were not available. The hosted artifact is implemented and tested, but its final cache policy remains a deployment responsibility.
